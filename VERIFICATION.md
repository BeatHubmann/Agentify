# Agentify: verification ledger

> **Status:** accepted with `ARCHITECTURE.md` at gate G2 on 2026-10-14 (PR #1). Slice 1 evidence is recorded as E-1; every other row stays *proposed* or *deferred* until evidence is recorded.
> **Authority:** `genesis/PRODUCTION-BRIEF.md` (cited as "§n") is the specification; `ARCHITECTURE.md` (cited as "A§n") is the design. This file maps each requirement to the evidence that will prove it. It adds no requirements.
> **Date:** 2026-10-14.

## Purpose

This ledger maps each requirement (invariant, hazard, behavior contract, definition of done, open problem, success criterion) to a proof obligation. Each obligation has a scenario, a test layer, an independent oracle and a negative control: a realistic broken implementation that the check must catch. "Implemented" and "verified" are separate statuses. A test file that exists is not evidence. A run of that test, recorded as below, is.

## Status vocabulary

| Status | Meaning |
|---|---|
| proposed | Obligation agreed at design time; nothing implemented |
| implemented | Mechanism and check exist in the repository; no recorded passing run on the current revision |
| verified | The check ran and passed on a recorded revision; evidence fields below are filled in |
| failed | The check ran and failed; the row links the failure record |
| not run | Prerequisite missing (environment, data, operator input); never counts as passed |
| not applicable (reason) | The requirement does not apply in scope; the reason is stated in the row |
| waived (owner, rationale) | An operator-named owner accepted the gap, with a written rationale and date |
| deferred (release 2) | Simulation and business case (OD-12; §12.4 step 7) |
| deferred (OD-12) | Regulatory mapping (§12.4 step 8; §13.2.4 unanswered) |
| deferred (OD-14) | Open problems 8, 12, 14, deferred by operator decision |
| deferred (OD-15) | Optional capabilities of §5.1 (archive import/export, live preview, demo sessions, maturity assessment), none in release 1 |

## Rules

- **Moving to verified.** A row becomes *verified* only when it records: the command and test selection; the exact revision (commit SHA); the environment and data versions (image digest, corpus version, rule-pack version, prompt version where relevant); the counts (selected, passed, failed, skipped); the date and time in CET/CEST and UTC; and the location of the log or artifact. The negative control must also have been run once and failed as expected, and that run is recorded. A command that discovers zero tests is a failure, not a pass.
- **Invalidation.** A change to the mechanism, the check or their dependencies returns affected rows to *implemented* until they are re-run. Evidence from an earlier revision can be reused only with a stated dependency rationale.
- **Change control.** Changing an approved acceptance criterion (an oracle, a threshold, a scenario, or a row's scope) requires an explicit operator decision. That decision is recorded separately from the implementation change (decision record with date, owner and reason), so a reviewer can see that the goalposts moved. An oracle is never changed after seeing a candidate result just to make it pass.
- **Synthetic versus real.** Synthetic corpus results (OD-17) are harness evidence only. Rows that depend on the product corpus are marked "blocked on real corpus". They can move only to *not run*, never to *verified*, until the operator supplies the real corpus.
- **Local versus production sandbox.** `sandbox-local` results exercise logic only. They are never evidence for INV-9; only `sandbox-drill` is (A§14.5).

## Release scope

- **Release 1 (OD-12):** the foundation (§12.4 steps 1–4), node profile and governance (step 5), and acceptance contracts and conformance (step 6). These rows are *proposed*.
- **Release 2:** simulation and business case (step 7). These rows are *deferred (release 2)*. The profile fields they read are collected in release 1 (OD-16).
- **Not scheduled:** regulatory mapping (step 8), until the operator answers §13.2.4. These rows are *deferred (OD-12)*.
- **Not in any release yet:** the optional capabilities (OD-15), the frontend (OD-11, D-9).

## Layer vocabulary

These are the suites of A§26.2: `unit`, `property`, `analytic`, `orchestration`, `failure`, `api`, `sandbox-local`, `smoke` (built-image smoke suite), `sandbox-drill`, `e2e-canary` and `evals`. Three more layers are used here. `human` means sampled or operator review. `static` covers the DoD-code pipeline checks of A§26.4 (ruff, mypy `--strict`, import-linter, registry validation, the AST registry-id lint, `typos`, gitleaks, translation parity and CI configuration) plus the tested-documentation check of A§26.1; it is not a test suite but the set of CI checks. `ops` means measurement in a deployed environment from run records, the ledger and the observability backend, with each alert rule shown to fire once on a planted condition in staging (A§21.1).

## ID conventions

- `INV-n` rows carry the brief's "verify with" obligation (§10). For INV-1 to INV-7 and INV-10, `INV-n.X` sub-rows with an exit-path suffix exist only where A§22.2 gives a distinct mechanism. The exit-path suffixes are: S success, ME model error, VF validation failure, UC user cancel, CD client disconnect, RC runtime-level cancellation (A§8.5, HZ-12, §12.5B), PK process kill or stall, SF storage failure, CR concurrent runs, UE user edits during a run.
- A hyphenated qualifier after an exit suffix (for example `INV-1.VF-TRUNC`, `INV-1.PK-STALL`) splits one exit path into separately controlled mechanisms, each with its own negative control.
- A word suffix without an exit letter (for example `INV-3.INTENT`, `INV-7.GC`, `INV-11.EXEMPT`) names a mechanism of A§22.1 that is not tied to one exit path.
- Where A§22.2 or A§22.4 says "As ME", no separate sub-row exists; the parent row names the sub-row that covers it.
- INV-8, INV-9, INV-11, INV-12 and INV-13 have exit-path columns in A§22.4. Their sub-rows name the exit (A§18.2), the isolation part (A§14.5) or the mechanism that the brief's "leak drill per exit" and "escape tests" require; a row that covers an A§22.4 cell cites that cell in its source. INV-10's `T-*` sub-rows name artifacts of the read-tolerance table (A§22.3).
- `SEM-n` rows pin the execution semantics of A§6.1.1, which invariants 1, 11 and 12 depend on. `OPS-n` rows are the operational contracts of A§21.1 (§12.1 layer 5). `DOC-n` rows cover tested documentation (A§26.1). Deviations (D-n, A§25) have no rows of their own; the rows of the mechanisms they change cite them.

## 8. Unproved at design time

These obligations cannot reach *verified* from design work alone. Each needs implementation, an environment, or operator input.

- **Real golden corpus (OD-17).** About 10 anonymized multilingual specifications in the private EU store. Blocks DOD-product.*, SC-1, SC-8, BC-D.1 (real part), BC-E.6, BC-F.6, HZ-26 (eval part) and the release-1 gate. Synthetic cases never count.
- **Human anchors and reviewers.** About 20 human-scored anchors per judged dimension, the 10% re-review loop, and named human baseline approvers (BC-D.11, BC-F.6, DOD-product.6).
- **Broken reference implementations** of golden nodes for the mutation check (BC-F.4, HZ-27, DOD-product.5).
- **Database residency (O-1).** Whether Fly Managed Postgres stores backups in the EU decides between Fly MPG and AWS RDS (OD-3). Until Fly confirms in writing, the residency of database backups is unproved.
- **Sandbox drills against the real sandbox organization** in staging (INV-9.*, BC-C.9, OP-3, SC-10, OPS-7). These need the separate Fly organization with its static egress addresses, the OIDC federation, the IAM trust policies, both public sandbox services (model gateway and exchange) and a drill-controlled DNS server and probe host. Local-adapter results do not count.
- **Platform facts still open.** Machines API acceptance of `image@sha256:` (O-3); whether Fly egress policies cover all egress (A§14.5); Bedrock data retention in every EU destination region (O-4); the IAM chain for application inference profiles (O-5); whether refusing Claude Code's `/inference-profiles` calls has side effects (O-6); whether root init can restrict `/.fly/api` to root (O-7, INV-9.SOCK; if not, the OIDC factor is dropped for model calls and INV-9.GWA is re-scoped by operator decision); the Fly proxy idle timeout, which so far rests on community posts (R2.7) and affects the client stream's keep-alive interval (the disconnect decision itself rests on the database attachment heartbeat, INV-1.CD).
- **Framework behavior at pinned versions.** Spike S1 ran against Pydantic AI 2.56 (code and output in `spikes/2026-10-14-pydantic-ai/`, A§28). The cancellation, retry-counter, concurrency, exception-propagation and finish-reason findings behind INV-1.RC, INV-1.VF-TRUNC, HZ-6, HZ-9, BC-B.2 and BC-B.3 must be re-confirmed at the versions pinned during scaffolding. Detecting framework-generated retry prompts from the message history (A§10.3) is not yet confirmed by a spike.
- **Operator approvals at G2.** The rule pack `agentify-core@1.0.0` with its four blocking rules, `exempting_provenance` default and the autonomy ceilings; the waiver-review threshold; the starting error-budget limits (5 per tool, 8 per class, 20 per run); the gate thresholds (`min_nodes` 3 and 2, `max_shrink` 30%); the disconnect grace period (15 s); the `intent_confirmation` validity window (not yet stated in A§8.2); the conformance iteration budget (3). - **Deferred scopes.** These need operator scheduling: release 2 (simulation), OD-12 (regulatory: §13.2.4 answers, the first catalog, an expert-labelled scenario set), OD-15 (archive import/export, preview), and OD-11 (frontend design-system document, which the brief's frontend test layer and the frontend checks of DoD-code depend on).
